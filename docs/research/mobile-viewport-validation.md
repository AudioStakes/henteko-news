# スマホの1画面表示とレイアウト検証の調査

調査日：2026年10月21日（日本時間）。
対象は、へんてこニュースのフッターを含む内容がスマホの表示領域からはみ出す問題と、その再発防止方法です。
この文書は修正前の調査と提案を記録しています。
その後の実装と回帰検証は[開発ガイド](../DEVELOPMENT.md)と`tests/layout/mobile-viewport.spec.ts`を参照してください。
本番公開は別途明示されたリリース時にだけ行います。

## 推奨する方針

通常の縦向き・標準文字サイズでは、トップ、単語選択、ニュース結果の各画面を、フッターまでスクロールなしで表示することを目標にします。
初期の必須条件は320 × 568、360 × 640、375 × 667、390 × 844、430 × 932 CSS pxとし、その間の幅・高さとCSSの切り替わり前後も確認する案です。
これらより低い表示領域、横向き、文字拡大、設定画面は別の到達可能性検査とし、合格条件を実装前に固定します。
端末名の一覧だけに依存せず、**表示領域の幅と高さの境界を検証するPlaywrightテスト**を中心にし、少数の画像比較と実機確認を組み合わせることを提案します。
端末エミュレーションはユーザーエージェント、画面・viewportの大きさ、タッチなどを模倣しますが、PlaywrightのWebKitはSafari本体ではありません。
このため「指定した条件で機械検査に合格した」と「すべての実機で崩れない」は区別します。[Playwrightの端末エミュレーション](https://playwright.dev/docs/emulation)、[WebKitとSafariの違い](https://playwright.dev/docs/browsers#webkit)

横向き、極端に低い表示領域、文字拡大、長い設定画面では、内容と操作性を保つための縦スクロールを許す設計を提案します。
WCAGの文字拡大は200%まで内容・機能を失わないことを求め、リフローは320 CSS px幅などの条件で二方向スクロールを避ける要件です。
すべての条件でスクロールを禁止する要件ではありません。[文字拡大](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)、[リフロー](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

## 表示領域に合わせるときの注意

### 現状の構造と確認できた原因

主担当のコード調査では、[`AppView.tsx`](../../src/components/AppView.tsx)でフッターが`.child-stage`の外にあります。
[`global.css`](../../src/styles/global.css)では`.child-stage`自体に`100svh`から上端余白を引いた最小高さがあり、その後ろにフッターの高さが加わります。
フッターには上下の余白と44 px以上のボタンがあり、その合計で少なくとも87 pxが追加されます。
下記の測定でも全42ケースでフッター全体が表示領域に収まらず、画面の高さを使う領域の外にフッターを積む構造が見切れの原因と確認できました。
viewport単位を変えるだけでなく、フッターを含めた画面全体で高さを配分する必要があります。
ブラウザのバーなど、実機固有の挙動まで原因を特定したものではありません。

既存の[`select-screen.spec.ts`](../../tests/layout/select-screen.spec.ts)には、対象を`scrollIntoViewIfNeeded()`してから可視性を確認する箇所があります。
これを、スクロール前に主要内容とフッターが同時に画面内へ収まる検証で補う案を提案します。
既存の`test:layout`とChromium・Firefox・WebKitなどのPlaywright projectsを利用できるため、別の検証基盤を新設する必要はありません。

### ローカルでの表示領域別測定

公開版`8fcaebc`の本番indexとローカルdistのindexが、同じJavaScriptファイル`/assets/index-BdZvv0rN.js`を参照することを確認したうえで、ローカルのビルドをPlaywrightで測定しました。
本番が参照するCSSも`/assets/index-DUXOSPAP.css`で、ローカルの同ファイルと内容が一致しました（SHA-256：`72607e529148d6c45bb69d871cf7130f01615ad569424e65d02b432391fc0ffd`）。
HTML全体のバイト列は異なるため、この照合を配信環境ごとの全挙動の一致保証とは扱いません。
使用したのはChromiumのデスクトップcontextで、CSS viewportだけを次の6種類に変更しています。
モバイル実機や`isMobile`を使う端末プリセットでの測定ではありません。

各表示領域について、トップ、単語選択5画面、ニュース結果の計7画面へ通常の操作で遷移し、合計42ケースを測定しました。
乱数は`0.5`に固定し、各画面のスクロール位置が0の状態で判定しています。
以下はChromiumで測定した内容高さの表です。
高さはCSS pxで、選択画面の列には5画面の最大値を示します。

| 表示領域（幅 × 高さ）   | トップの内容高さ | 選択画面の最大内容高さ | 結果の内容高さ |
| ----------------------- | ---------------- | ---------------------- | -------------- |
| 320 × 568               | 782              | 940                    | 750            |
| 360 × 640               | 822              | 964                    | 793            |
| 375 × 667               | 829              | 970                    | 804            |
| 390 × 844               | 931              | 975                    | 931            |
| 430 × 932               | 1,019            | 1,019                  | 1,019          |
| 667 × 375（横向き相当） | 845              | 988                    | 827            |

全42ケースでフッターの全体表示に失敗しました。
特に430 × 932では全画面の内容高さが表示領域より87 px大きく、フッター相当の高さが外に積まれていることが測定からも分かります。
小さい表示領域では中央のコンテンツも高くなっているため、フッターの置き場所だけでなく、イラスト・余白・カードを含む高さの配分も調整する必要があります。
選択肢と結果文の最長組み合わせは網羅していません。

追加でWebKitでも同じ6種類・7画面の42ケースを測定し、Chromiumと合わせた計84ケースすべてでフッター全体が表示領域に収まらないことを確認しました。
375 × 667では各画面の内容高さもChromiumと同値でした。
両エンジンともデスクトップcontextのCSS viewportを変更した測定であり、モバイル実機での確認ではありません。

### CSSとブラウザの挙動

| 項目         | 一次資料で確認できた挙動                                                                         | このアプリへの提案                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `vh` / `lvh` | 現在の既定のviewport単位は大きいviewportに対応し、ブラウザのバーが現れると内容が隠れる場合がある | `100vh`だけを根拠に「画面内」と判定しない                                      |
| `svh`        | ブラウザのバーを表示した小さいviewportを基準にし、バーが閉じても高さが安定する                   | 最小表示高さに収まるレイアウトの設計基準にする。バーを閉じた状態では余白が出る |
| `dvh`        | バーの開閉に応じて値が変わる。更新には間引きなどがある                                           | 現在の表示高さを使って外枠を満たす候補。操作中の再配置が気にならないか確認する |
| `min-height` | 高さの下限を指定し、内容が増えれば要素は高くなれる                                               | `min-height: 100dvh`だけではフッターの見切れを解決したことにならない           |

出典：[MDNのviewport単位](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length#relative_length_units_based_on_viewport)、[動的viewportの制約](https://web.dev/blog/viewport-units)、[min-heightの定義](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-height)

実装時は、利用可能な高さからヘッダーとフッターの場所を確保し、中央のイラスト、余白、カードの高さの順に調整する案が適しています。
固定の下マージンを減らすだけでなく、内容が収まるかを各画面で確認します。
`overflow: hidden`で見切れを隠したり、画面全体を無制限に縮小したりする方法は、このアプリの操作性を損なうため採用しないことを提案します。

ノッチやホームインジケーターのある端末ではsafe areaも確保します。
`viewport-fit=cover`で全面を使う場合、重要な内容に`env(safe-area-inset-*)`を考慮した余白が必要です。
safe areaは通常の余白の代替ではないため、両方を考慮します。[WebKitの説明](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)

キーボードやピンチズームでは、レイアウト用のviewportを変えずに実際に見える範囲だけが縮む場合があります。
`dvh`に変えるだけでキーボードへの対応まで完了するとは扱いません。
入力フォームがある場合は、入力欄と確定・閉じる操作に到達できることを別条件で確認します。[VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)、[キーボードとviewport単位](https://web.dev/blog/viewport-units)

ホーム画面に追加したPWAの`standalone`表示ではURLバーがなく、通常のブラウザ表示と利用可能な高さが異なります。
ステータスバーなどは残る場合があるため、通常表示とPWA表示を実機確認の対象にします。[manifestのdisplay](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display#standalone)

## 機械検証の構成案

以下は一次資料を踏まえたこのアプリ向けの提案です。
まず既存のPlaywright構成を拡張し、新しいテストツールの導入は避けます。

### 1. 多くの条件をDOMの位置・寸法で検査する

通常の縦向き画面では、各画面への遷移直後・スクロール前に次を検査します。

- フッター、主要ボタン、カード、結果文の全体が表示領域内にあること。`toBeInViewport({ ratio: 1 })`を使用する。
- documentの`scrollHeight`と`scrollWidth`が表示領域を超えないこと。丸め誤差の小さな許容値を設ける。
- 要素の矩形が親の領域からはみ出していないこと。固定フッターや`overflow: hidden`で欠落を隠していないかも確認する。
- 結果文・ボタンラベルの内部に文字の欠けや意図しない折り返しがないこと。要素全体の矩形だけでなく内部の描画範囲も確認する。
- 重なってはいけない主要領域の矩形が重ならないこと。キャラクターと吹き出しなど意図した装飾の重なりは対象外にする。
- 操作ボタンをタッチで操作できること。主要ボタンの大きさを縮めて収める変更を検知する。

単語選択では、短い語の2／1／2配置と、8文字超の語があるときの`.long-choices`による縦5枚配置を、乱数任せにせずそれぞれ固定した入力で検査します。
結果の最長文に加え、オフライン通知、音声の読み込み中・失敗など、高さを追加する状態も別ケースにします。

`toBeVisible()`だけでは「全体が画面内に収まる」ことを保証せず、`toBeInViewport()`も既定では一部の交差で合格します。
またクリックなどは自動で対象までスクロールするので、通常の操作E2Eに合格しても初期表示の見切れは残り得ます。
位置の検査を操作前に行う理由はこのためです。[viewport検査のratio](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-be-in-viewport)、[操作時の自動スクロール](https://playwright.dev/docs/input#mouse-click)

主な操作ボタンの下限は44 CSS px以上を提案し、子ども向けの現在の大きさを維持することを優先します。
44 pxはWCAGの強化基準であり、最低基準は24 pxまたは所定の間隔などです。
44 pxという数値を「5歳児で検証された最適値」とは扱いません。[ターゲットサイズの強化基準](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)、[最低基準](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

文字拡大・横向きなどの例外条件では、縦にはみ出さない検査を適用せず、横にはみ出さないこと、隠れずにスクロールして読めること、主要操作に到達できることを検査します。
すべてのDOM要素を一律に「重なり禁止」とする検査は、装飾に対する誤検知が多いため避けます。

### 2. 幅だけでなく高さの境界を選ぶ

| 検証条件の候補                                     | 目的                                               |
| -------------------------------------------------- | -------------------------------------------------- |
| 幅320・360・375・390・412・430 CSS pxの代表値      | 狭い端末から幅広い端末までの列数・改行・横はみ出し |
| 小さい高さ、ブラウザバー表示相当の高さ、通常の高さ | フッターを押し出す縦方向の不足                     |
| CSSの切り替わり幅・高さの前後1 px                  | 境界でのレイアウト崩れ                             |
| ChromiumとWebKitの代表条件                         | エンジン間のレイアウト差                           |
| 最長の単語・結果文、読み込み中・音声エラーなど     | 内容の長さと状態による高さの変化                   |
| 横向き・200%相当の文字拡大                         | 例外時にも内容と操作性を失わないこと               |

数値は端末の物理解像度ではなくCSS pxで管理します。
端末プリセットのviewportを上書きして高さを変えることも可能です。[Playwrightのviewport設定](https://playwright.dev/docs/emulation#viewport)
バー表示相当の高さへの変更は、狭い表示領域でのレイアウト確認です。
実際のSafariのバー開閉アニメーション、safe area、キーボードを再現した検証とは区別します。

### 3. 少数の画像比較で見た目を確認する

最小寄りの縦画面と標準的な縦画面などに絞り、各主要画面を`toHaveScreenshot()`で比較する案を提案します。
viewport画像を使い、フルページ画像だけで「1画面に収まる」と判定しません。
乱数の選択肢・結果、音声状態、フォント・画像の読み込みを安定させ、アニメーションを無効化して撮影します。
OSやブラウザによって描画が異なるため、画像の基準作成と比較は同じCI環境で行います。[画像比較と実行環境](https://playwright.dev/docs/test-snapshots)、[アニメーションの無効化](https://playwright.dev/docs/api/class-locatorassertions#locator-assertions-to-have-screenshot-1)

DOM検査は見切れの理由を特定しやすく、画像比較は配色・配置・画像サイズなど数値条件にしにくい変化を見つける役割です。
画像差分を大量に増やすと基準更新の負担が大きいため、最初は少数に限定します。
失敗時にはviewport画像、幅・高さ、はみ出した要素とその矩形を保存すると、修正箇所を探す手戻りを減らせます。

### 4. 実機はリリース候補で重点確認する

iOS SafariとAndroid Chromeで、バーの表示・収納、縦横の切り替え、safe area、文字拡大を確認します。
PWAを提供する場合はホーム画面起動も確認し、入力欄がある画面はキーボード表示中の操作も対象にします。
通常の変更ではDOM検査を広く回し、画像比較を少数に絞り、これらの実機確認をリリース候補で行う構成を提案します。
必要になった段階で実機クラウドを検討でき、初期段階から新たな有料サービスを導入する必要はありません。

既存のGitHub Actionsは手動実行の運用です。
自動検査の実行方法は別途決めるものとし、この提案を理由にGitHub Actionsの実行契機や停止中のNetlify自動ビルドを変更しません。
ローカルまたは手動CIで検査し、明示されたリリース時にだけNetlifyへ公開する運用を維持します。

上記の修正前調査ではアプリ・テスト・Netlify設定を変更していません。
全実機の保証や、ピンチズーム・キーボード・ブラウザバー挙動の実機検証は実施していません。
